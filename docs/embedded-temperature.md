# Embedded CPU temperature

Nexo uses the official LibreHardwareMonitorLib NuGet package 0.9.6 inside its own process. It enables CPU hardware only and opens, updates, and attempts to close the computer for each measurement, including error/cancellation paths. No standalone Libre Hardware Monitor program or WMI publisher is needed.

In LibreHardwareMonitorLib 0.9.6, `Open()` can fail after acquiring resources but before marking the computer open; `Close()` can then return without releasing that partial initialization. Nexo cannot guarantee cleanup in that upstream failure path. A process-wide circuit breaker prevents any later `Open()` after an initialization failure and reports that restarting Nexo allows another attempt. Read/update failures after successful initialization do not trip this breaker. Storage collection remains independent.

CPU register access requires the PawnIO driver on supported Windows hardware. Missing PawnIO gives `no_source` and a null temperature. A present driver does not guarantee access: permissions, platform support, or security settings may leave `no_sensor`/`error`. No estimated temperature is substituted. The driver check is the LibreHardwareMonitorLib rule (a valid `DisplayVersion` under `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\PawnIO`, default and 64-bit views), re-read on every call by `PawnIoDriver.Installed()`, because the library caches it once per process.

On the development host, a standard non-administrator process detected installed PawnIO 2.1.0.0 with its service running, but opening the PawnIO device with the library's ReadWrite access returned Windows error 5 (access denied). LibreHardwareMonitorLib 0.9.6 exposed only `Core (Tctl/Tdie)`, returning raw zero on two updates one second apart. This is not a real temperature reading; Nexo reports `invalid`, null Celsius, and a possible hardware-access permission limitation. With Nexo elevated, the same sensor read 63.8 °C. Driver installation alone does not resolve that permission boundary.

## Decision (#142): optional install and a separate elevated reader

The previous rule ("Nexo does not install PawnIO or launch its installer") changed. Nexo still never installs the driver on its own and never runs its full process as administrator:

- **Install, only on user request.** In PC Health (temperature unavailable without PawnIO) and as card 04 in Tools, "Instalar PawnIO (driver oficial)" first shows Nexo's confirmation dialog: third-party kernel driver (PawnIO, by namazso, GPL-2.0), official GitHub release 2.2.0, UAC prompt, the PawnIO wizard does the install, uninstall via Settings > Apps > PawnIO. Then `PawnIoSetup` downloads `https://github.com/namazso/PawnIO.Setup/releases/download/2.2.0/PawnIO_setup.exe` over HTTPS with automatic redirects disabled; each redirect must stay on `github.com`, `objects.githubusercontent.com` or `release-assets.githubusercontent.com` (port 443, no user info). The file goes to a fresh `%TEMP%\Nexo\PawnIO\<guid>` folder and must be exactly 3410960 bytes with SHA-256 `1f519a22e47187f70a1379a48ca604981c4fcf694f4e65b734aaa74a9fba3032`; otherwise it is deleted and nothing runs. `Get-AuthenticodeSignature` must report `Valid` (the same check used for the NVIDIA package); the signer subject is recorded in the result, the audit log and the operational history. The file stays open without write/delete sharing from hashing until the installer exits. While it is open, its parent folders cannot be renamed; Nexo then refuses to run it if the file or any folder above it, up to the volume root, is a link or junction (a junction could be re-pointed before the UAC prompt). Same-user code can still drop files next to the installer before it runs; this stays within the limit noted for the elevated reader below. The installer itself runs through ShellExecute `runas`, with no silent flags, and is deleted afterwards. The result is one of: installed, UAC canceled, failed with exit code, not installed (wizard closed), integrity (size/hash), signature (invalid or not checkable), link (junction in the path), host (redirect refused) or network. The version is pinned: Nexo never queries "latest" and never uses the "Unrestricted" edition.
- **Read, one UAC per click.** When PawnIO is installed but the in-process reading is not usable, "Ler temperatura (pede administrador)" starts `Nexo.exe --read-sensors <file>` with `runas`. That mode opens no window, takes no mutex, loads no user data and accepts exactly one argument: a file named `reading-<32 hex>.json` directly inside `%ProgramData%\NexoSupport\sensors`; anything else exits with code 2 before touching hardware. Without administrator rights it exits with code 3. The elevated process creates `NexoSupport` and `sensors` with the protected descriptor used by the network and debloat executors (owner Administrators, inheritance off, SYSTEM and Administrators full control, Users read-only); an existing folder is only used if it already passes the same trust check (`NetworkRecovery.UntrustedItem`), otherwise code 4. It reads the CPU sensors once (GPU is not read), writes the JSON (format, time, state, Celsius, sensor, source, detail) as a new protected file, removes older readings and exits. The app waits up to 20 s, re-checks the folders and the file, and accepts only state `read`, 0–125 °C, a time after the request (1 min clock tolerance) and less than 5 minutes old. The screen then shows, for example, "63,8 °C · Core (Tctl/Tdie) · leitura com administrador às HH:mm". UAC cancelation, timeout, exit codes, untrusted files and invalid JSON become explicit states, never a value. The reading is shown only while PC Health stays open; nothing loops or asks for UAC by itself. Known limit: this mode runs `Nexo.exe` from `%LOCALAPPDATA%\Programs\Nexo`, a folder the user can write, so code already running as the same user can change what the elevated process loads (`Nexo.dll`, side-by-side DLLs, `Nexo.runtimeconfig.json`, `DOTNET_*` variables). The same limit already applies to the elevated executor; moving Nexo to a per-machine folder under Program Files would remove it.
- **Health report.** For up to 5 minutes, when the regular reading is not `read`, `get_health_report` uses the elevated reading in the temperature line, with its source and time ("lida às HH:mm com administrador, a pedido do usuário").
- **Model guardrails stay.** The assistant still must not offer to verify, install or look for PawnIO (#135); the buttons are UI-only.

## Live temperature: the system sensor reader (#142, option 2)

PC validation on 23/11 (Windows 10 22H2, Ryzen behind AMD-RAID, PawnIO 2.2.0): the elevated reading returned 78.6–80.2 °C, the non-elevated reading stayed at zero. To show the temperature live without running Nexo as administrator, the user can install a minimal system reader once.

- **Activation, only by click.** In PC Health, with PawnIO installed, **Ativar temperatura ao vivo** opens Nexo's confirmation dialog: a minimal sensor reader is copied to a protected folder under Program Files, runs as a SYSTEM scheduled task from startup and writes only the temperature; Windows asks for UAC once; how to turn it off.
- **Elevated install, one UAC.** The script runs through the supervised elevated executor (the debloat one: `OptimizationDiskExecutor` + `NetworkRecovery.Compact`), starts with the PSModulePath guard (#131) and reuses the protected-folder functions of the network executor (`ProtectedFolderScript`). It (a) creates `%ProgramFiles%\Nexo` and `%ProgramFiles%\Nexo\Sensors` with the protected descriptor (owner Administrators, inheritance off, SYSTEM and Administrators full control, Users read and execute); an existing folder that inherits permissions, has a user-writable ACE, a non-trusted owner or is a reparse point is refused before anything is stopped, copied or registered; (b) copies from the running app folder only what the reading mode needs: `Nexo.exe` for the published single-file build, plus any top-level native `.dll` left beside it (a single-file publish without `IncludeNativeLibrariesForSelfExtract`, as in the README command and the official build, leaves the WPF natives such as `wpfgfx_cor3.dll` next to the `.exe`; without them in the protected folder, `Nexo.exe` as SYSTEM would look for them through the Windows DLL search order, which reaches the `PATH` folders), or the top-level `.exe`/`.dll` plus `Nexo.runtimeconfig.json` and `Nexo.deps.json` of a build folder. The elevated process opens each source file with read sharing only (no writer can open it meanwhile), hashes that same handle with SHA-256, copies from it into a temporary file created with the protected descriptor, re-hashes the copy and only then moves it into place; files of an older copy that are no longer needed are removed; (c) registers the task **Nexo Sensores** as SYSTEM, `AtStartup`, restart on failure (every minute, up to 999 times), no execution time limit, below-normal priority, single instance, with the action `%ProgramFiles%\Nexo\Sensors\Nexo.exe` (Execute), `--sensor-loop` (Argument) and `%ProgramFiles%\Nexo\Sensors` (WorkingDirectory); a path with `%` (expanded by Task Scheduler) or `"` is refused; (d) starts it. The install, update and removal go to the audit log and the operational history like the other tools.
- **Direct task action, protection inside the process (P9).** The first version ran `cmd.exe /d /c set "PATH=…" && set "DOTNET_BUNDLE_EXTRACT_BASE_DIR=…" && "…\Nexo.exe" --sensor-loop`. PC validation on 23/11 showed the defect: `schtasks /End` (and `Stop-ScheduledTask`) ends only the `cmd.exe`; the `Nexo.exe --sensor-loop` child stays orphaned and keeps writing, so "sem resposta" never appears, `/Run` starts a new instance that exits on the mutex while the old PID goes on, and the task's restart-on-failure does not cover the orphan. The task now runs `Nexo.exe` directly, so ending the task ends the reader. The two protections that the command line gave moved into the process:
  - **DLL search order.** `Nexo.exe` has its own `Program.Main` (`StartupObject`). The WPF-generated `Main` creates `App` and runs `InitializeComponent` (App.xaml: theme dictionaries, fonts, geometries) before `OnStartup`, so branching there was too late. The first statement of `Program.Main` routes `--sensor-loop` to `SensorLoopEntry.Run`, before any WPF type is touched (the normal app starts in a separate non-inlined method). `SensorLoopEntry` first calls `SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_APPLICATION_DIR | LOAD_LIBRARY_SEARCH_SYSTEM32)` (kernel32). From then on, a DLL loaded without a full path and the dependencies of native DLLs are looked up only in the protected folder and in System32, never in `PATH` or the current folder. If the call fails, the loop exits with code 5 and nothing else runs. Right after it, the process `PATH` is set to `System32;Windows;System32\Wbem`, built from `Environment.GetFolderPath(System)` and `GetFolderPath(Windows)` and never from the inherited environment (no `%SystemRoot%` or `%windir%`), which restores the protection the old `cmd.exe` command line gave for anything that still consults `PATH`; if those folders are not fully qualified, the loop also exits with code 5. The runtime loads the native DLLs that ship next to the `.exe` (the WPF natives) by full path from the protected folder. Known limit: for a DLL loaded by full path with `LOAD_WITH_ALTERED_SEARCH_PATH`, which the runtime uses for P/Invoke without `DefaultDllImportSearchPaths`, Windows documents an alternate search order for that DLL's dependencies. The process-wide setting is not guaranteed to cover that order. In practice every dependency is found in the protected folder or in System32 before any other folder is tried. The PC check confirms this: the loop's module list has nothing outside `Sensors`, `System32` and `WinSxS`.
  - **No extraction.** Both published builds, the README command and the official `scripts/Build-CloudRelease.ps1` (the `nexo-app.zip` that NexoSetup installs), are single-file, self-contained, without `IncludeNativeLibrariesForSelfExtract`, and extract nothing: the WPF natives sit next to `Nexo.exe` and are copied to the protected folder. The official build used to pass `IncludeNativeLibrariesForSelfExtract=true` (QA finding B1, 23/11): every PC installed by NexoSetup got a task that always exited with 2, and the host had already extracted into SYSTEM's `%TEMP%` before `Main` on every start. The release script now refuses a package without `wpfgfx_cor3.dll` and `PresentationNative_cor3.dll` next to `Nexo.exe`. If a build ever extracted files, .NET would put them under SYSTEM's `%TEMP%` (`C:\Windows\Temp\.net`), where standard users can create folders. The loop refuses that with code 2. Detection uses the host's `NATIVE_DLL_SEARCH_DIRECTORIES` runtime property: without extraction it lists only the executable's folder; with extraction it also lists the extraction folder. The loop accepts single-file only when every entry is `%ProgramFiles%\Nexo\Sensors`. Entries that are missing, relative, or point anywhere else are refused, including an old `Sensors\extract`. .NET 8 exposes no `BUNDLE_EXTRACTION_PATH` property (checked against the 8.0 host and with a single-file probe, with and without self-extract). A build folder (not single-file) keeps the previous rules. The app applies the same rule (`Extracted`) to its own process before the confirmation and the UAC: when the running Nexo is single-file and its `NATIVE_DLL_SEARCH_DIRECTORIES` lists any folder other than its own, **Ativar temperatura ao vivo** and **Atualizar leitor** stop with "Esta compilação do Nexo não suporta o leitor de sensores do sistema… Reinstale o Nexo com a versão atual do NexoSetup", so a task that would always exit with 2 is never registered. **Desativar** is never refused.
- **`--sensor-loop` mode.** Opens no window, loads no user data, takes no mutex of the UI and accepts no extra argument. It exits with code 5 if the DLL search order could not be restricted or the `PATH` could not be fixed, 2 if the executable is not exactly `%ProgramFiles%\Nexo\Sensors\Nexo.exe` (so it never runs as SYSTEM from the user's folder) or if the single-file extracted files, 3 if it is not SYSTEM, 4 if the install folder or `%ProgramData%\NexoSupport\sensors` fails the trust check, 0 if another loop already runs (global mutex), 6 if the sensor cannot be opened (LibreHardwareMonitorLib 0.9.6 cannot safely reopen in-process; the task restarts it). It opens one CPU-only LibreHardwareMonitor session, reads every 2 s at below-normal priority and atomically replaces `%ProgramData%\NexoSupport\sensors\live.json` (protected temporary file, then move) with `{Format, Kind, Time (UTC), State, Celsius, Sensor, Detail, Version, Pid}`. On a reading error it writes the error state with no value. The file is replaced, never appended, and its detail is truncated, so it stays below 4 KB.
- **Reading by the app without admin.** Each render of Home and PC Health and each visible tick of the "Agora" card (1 s, paused like `LiveMetricsPanel` when the screen is not visible) reads `live.json` synchronously, with read/write/delete sharing so the reader's move is never blocked. The app trusts it only when the reader is installed, `NexoSupport`, `sensors` and the file pass `NetworkRecovery.UntrustedItem` (owner and ACL), the file is under 4 KB, valid JSON in the expected format, plausible (0–125 °C, sensor named) and less than 10 s old (5 s clock tolerance). Then the temperature appears live as a "Temperatura" block in the "Agora" card, in PC Health ("78,6 °C · Core (Tctl/Tdie) · ao vivo, leitor de sensores do sistema, às HH:mm:ss"), in the Home "Estado do computador" already on the first render after opening Nexo, and in the health report and chat with the source "leitor de sensores do sistema" and the time. Without a fresh file right after boot (a file from before the last startup, up to 2 min), it shows "Temperatura: aguardando o leitor…", never "indisponível". An older file shows "leitor de sensores sem resposta desde HH:mm". With no `live.json` at all, "aguardando" lasts only 2 min after boot or after the activation/update (the write time of the protected `Nexo.exe`); after that the reader never wrote anything (exit code 2, 3, 4 or 6, or a task that does not start) and the screen shows "leitor de sensores sem resposta desde HH:mm, sem nenhuma leitura gravada". Wrong owner or ACL, invalid or oversized JSON are ignored with the reason, never shown as a value.
- **Report and chat.** With a valid reading (system reader or elevated), the non-elevated zero reading ("retornou zero… descartada") is no longer sent to the model, neither in the temperature line nor in the limitations (both the "Sensor de temperatura da CPU indisponível" line and the sample warning "Temperatura da CPU: …" that the collector stores in `HealthSnapshot.Warnings`). With PawnIO installed and the sensor at zero and no valid reading, PC Health and Home show a neutral state ("A temperatura precisa de permissão de administrador. Ative a temperatura ao vivo"), and the report says the missing permission does not indicate a driver defect. "Descartada" still applies to other invalid readings.
- **Turning it off.** PC Health > **Desativar temperatura ao vivo** (one UAC): stops the loop (`Stop-ScheduledTask`, then every `Nexo.exe` whose `Win32_Process.ExecutablePath` is exactly `%ProgramFiles%\Nexo\Sensors\Nexo.exe`, case-insensitive like Windows, is ended with `Stop-Process`; a `Nexo.exe` from any other path is never touched; if the reader is still running after 10 s, nothing else is changed), removes the task, deletes `%ProgramFiles%\Nexo\Sensors` (including `extract`) without following links (any link inside stops the removal before the task is touched), removes `%ProgramFiles%\Nexo` if empty and deletes `live.json`. PawnIO stays installed (Settings > Apps > PawnIO). The installed version is shown. **Atualizar leitor** appears when it differs from the app's version, or when the version matches but the build differs: the `ProductVersion` of the installed `Nexo.exe` (the informational version, which the .NET 8 SDK completes with `+<commit>` in a git checkout) is not the running Nexo's. Without `+<commit>` on both sides, only the version counts. The button (one UAC) stops the loop the same way before copying, so the `Nexo.exe` orphaned by an install with the old `cmd.exe` action is ended too, re-copies with the same checks, re-registers the task with the direct action and starts it. Manual removal, if Nexo is gone: in an elevated prompt, `schtasks /End /TN "Nexo Sensores"`, `schtasks /Delete /TN "Nexo Sensores" /F`, end any `Nexo.exe` still running from `%ProgramFiles%\Nexo\Sensors` (an install with the old `cmd.exe` action leaves it orphaned) and `rmdir /S /Q "%ProgramFiles%\Nexo\Sensors"`.
- **Security model and limits.** SYSTEM only ever runs binaries from a folder that only administrators and SYSTEM can write, so code running as the user cannot change what the SYSTEM process loads afterwards. The copy is as trustworthy as the user's Nexo at the moment of activation: code already running as the same user could have changed the source before the UAC, the same limit as the elevated reader and the elevated executor. In a build folder (not the published single-file), `Nexo.runtimeconfig.json` and `Nexo.deps.json` are copied too, so a source changed before the UAC could also point the runtime at a user folder (for example `additionalProbingPaths`); use the published Nexo to activate the reader. A standard user can hold the global mutex name `Global\Nexo.Sensors` before the loop starts; the loop then exits with code 0 and the screen shows "sem resposta" (denial of service only, no code runs). The app-side checks only decide whether the number is shown; the file grants nothing. The model still must not offer to install, verify, activate or update any of this (#135); the guard now also covers "ativar a temperatura ao vivo" and "leitor de sensores".

Temperature and storage collection remain independent. Temperature has a 10-second managed wait limit. A native call cannot safely be terminated in-process; if it exceeds the wait limit or the caller cancels, disposal is attempted when that call returns. A process-wide gate prevents another hardware session from starting while the first still runs. The storage PowerShell process keeps its separate 15-second limit.
